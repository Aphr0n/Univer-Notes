# Частина 1. Загальна картина

## 1.1. Життєвий цикл розробки (слайд 2 в обох лекціях)

Діаграма однакова в обох лекціях:

- **Фази ліворуч:** Analysis → Specification → System Design → Module Design → Coding → Integration.
- **Тестування праворуч:** Module Test, Integration Test, System Test, Acceptance Test.
- Також є **Review**, **Correction** і **User Manuals**.
- **Пунктирні двосторонні стрілки** означають, що фази не строго послідовні: перевірки можуть повернути до попередніх етапів.

**Червоною рамкою виділено різні частини:**
- **Лекція 7**: верх діаграми (Analysis, Specification, System Design, Review, Correction, User Manuals).
- **Лекція 8**: середина (System Design, Module Design, Coding, Integration).

Тобто лекції ділять діаграму на дві частини: **Л7 = початок (зрозуміти, записати, спроєктувати), Л8 = реалізація (деталізувати, закодувати, зібрати)**. Системний дизайн лежить на стику й згадується в обох.

## 1.2. Що доводиться контролювати (слайд 3 в обох лекціях)

Є **етапи** і три **супровідні теми**, які менеджер контролює протягом усіх етапів.

| | Лекція 7 («Specification») | Лекція 8 («Development») |
|---|---|---|
| **Етапи** | Analysis, Specification, System design | System design, Module design, Coding, Integration |
| **Супровідні теми** | Quality, Documentation and evolution, Resources (люди, ПЗ, обладнання, гроші) | ті самі |

Аналогія з будинком: етапи це «розмова з клієнтом → список побажань → загальний план → проєкти окремих систем → будівництво → з'єднання систем». Супровідні теми це контроль якості, креслення й інструкції, і будівельники з бюджетом.

# Частина 2. Етапи

## 2.1. Аналіз домену і проблеми [Л7]

*Domain* = предметна область, «світ», у якому працюватиме система (наприклад, для системи лікарні це реєстратура, лікарі, картки пацієнтів).

- **Domain engineering**: систематично вивчити предметну область (поняття, правила, процеси).
- **Domain experts**: люди, які область знають зсередини (лікарі, а не програмісти). Без них розробник легко зрозуміє область хибно.
- **System engineering**: дивитися на систему як на **цілість**: не лише програма, а й обладнання, люди, процеси навколо.
- **Problem description(s)**: чітко сформулювати проблему. (s) натякає, що описів може бути кілька, бо різні сторони бачать проблему по-різному.
- **Requirements elicitation**: «витягування» вимог. Вони самі не лежать на поверхні, їх треба дістати з людей розпитуванням, спостереженням тощо.

**Підсумок:** вивчити область (з експертами) → побачити систему цілісно → сформулювати проблему → почати збирати вимоги.

## 2.2. Специфікація вимог [Л7]

### Requirements engineering (RE)
- **Talking to the customer**: розмова із замовником.
- **Negotiating specific requirements**: узгодження конкретних вимог. Замовник часто не знає, чого хоче, або хоче несумісного, тому потрібні домовленості.

### Function point analysis (FPA)
Метод **оцінки розміру системи за її функціями** (що система вміє: вводити дані, виводити звіти, зберігати файли тощо).
- **Based on the outputs of RE**: рахується на основі вимог, які вже зібрано.
- **Cost estimation** та **Resources estimation**: оцінка вартості та потрібних ресурсів.

Логіка: більше функцій → більша система → дорожча й довша розробка. Це та сама тема, що **UFP/VAF** у практичних завданнях.

### Техніки збору вимог (RE best practices)

| Техніка | Суть |
|---------|------|
| Interviews | розмови з людьми |
| Context-free questions | питання, не прив'язані до рішення: «Яку проблему це має розв'язати?» |
| Questionnaires | анкети; добре, коли людей багато |
| Requirements workshops | спільні зустрічі всіх сторін |
| Observation | спостерігати за реальною роботою користувачів |
| Document analysis | вивчати наявні документи |
| Analysis of existing systems | дивитися, що вже є й чого бракує |
| Prototyping | зробити прототип, щоб замовник міг щось побачити й відреагувати |
| Scenario-based elicitation | описувати сценарії використання |
| Objective and goal analysis | з'ясувати цілі замовника, не лише його побажання |

Чому багато способів: люди не завжди вміють сказати, чого хочуть, і одна техніка рідко дає повну картину.

## 2.3. Системний дизайн (Л7 слайд 7 + Л8 слайд 4)

Перші п'ять пунктів **однакові в обох лекціях**:

- **Always based on requirements**: дизайн завжди спирається на вимоги.
- **Prototyping specific parts to help with RE**: прототипи окремих частин допомагають **уточнити вимоги** (дизайн допомагає вимогам, зворотний зв'язок).
- **Architecting the system based on customers' needs**: архітектура будується під потреби замовника.
- **Designing the manuals and interfaces**: проєктування посібників та інтерфейсів.
- **Preparing for service and maintenance**: підготовка до підтримки вже на етапі дизайну.

**[Л8] Нове:**
- **(req. tracking)** біля першого пункту. **Requirement tracking** (відстеження вимог) означає, що кожен елемент дизайну можна **простежити до конкретної вимоги**: чому він існує. Це допомагає не робити зайвого й не пропустити потрібне. У таблиці вимог (див. 4.4) для цього є стовпець «ID of covered user story».
- **Systems requirements + system architecture**: з системних вимог і архітектури виникає **розподіл системи на модулі та їхніх відповідальностей**. Слайд посилається на CRC-картки (там вказано Lecture 06; CRC-картки є й у слайдах лекції 7).

Системний дизайн відповідає на питання: **«з яких великих частин складається система і за що кожна відповідає?»**

## 2.4. Дизайн модулів [Л8]

*Модуль* = невелика підсистема (частина системи, яку можна проєктувати й розробляти окремо). Приклад з будинком: «електрика» чи «опалення».

- **Modules are small subsystems (name, responsibility, collaborators)**: модуль описується трьома речами (така сама структура, як у CRC-картки).
- **More communication/interaction**: між модулями більше взаємодії, ніж на рівні всієї системи.
- **Complex interfaces**: інтерфейси між модулями складніші. *Інтерфейс* = «розетка», через яку модуль спілкується з іншими.
- **Selected subset of required functionality**: кожен модуль реалізує лише вибрану частину потрібної функціональності.
- **Developing guides for integration/usage**: розробляються інструкції, як модуль підключати й використовувати.
- **Setting limits of model functionality and operation**: встановлюються межі того, що модуль вміє й як працює. (У слайді написано «model», найімовірніше це описка, і мається на увазі «module».)

**Різниця між системним і модульним дизайном:**
- *Системний*: «які частини є і за що відповідають?» (загальна картина).
- *Модульний*: «як саме влаштована кожна частина і як вона підключається?» (деталі).

## 2.5. Програмування [Л8]

- **Code generation (MDA, tools)**: **генерація коду**. Частину коду можна не писати вручну, а отримати з моделей чи спеціальними інструментами. **MDA** = Model-Driven Architecture (архітектура, керована моделями): малюєте модель (наприклад, UML), інструмент генерує код.
- **Writing**: ручне написання коду.
- **Storage**: де зберігається код.
- **Versioning and teamwork**: **версіонування та командна робота**. Багато людей працюють над одним кодом, тому потрібні система контролю версій (наприклад, Git), історія змін і правила співпраці.
- **Verification**: перевірка, що код зроблено правильно.

## 2.6. Інтеграція [Л8]

*Інтеграція* = з'єднання окремих модулів в одну працюючу систему.

- **Code generation** та **Writing**: інтеграційний код може генеруватися або писатися вручну.
- **Configurations**: **налаштування** (як модулі підключаються, параметри середовища). Окремий пункт, бо на інтеграції конфігурація дуже важлива.
- **Verification**: перевірка, що з'єднане працює правильно.

Інтеграція це по суті «кодинг на рівні з'єднань» плюс налаштування.

# Частина 3. Якість (Quality assurance)

Слайд 8 в обох лекціях. Тут легко заплутатися, тому подано таблицею.

## 3.1. Ключові терміни

| Термін | Що означає | Лекція |
|--------|-----------|--------|
| **Inspection** (інспекція) | контроль **ПРОЦЕСУ**: чи все робиться як треба; включає перевірку й робочих версій документів | обидві |
| **Review** (рев'ю) | контроль **РЕЗУЛЬТАТІВ** процесів: фінальних документів (наприклад, специфікації вимог) | обидві |
| **Correction** (виправлення) | зміна в процесі або в документі за пропозиціями з inspection/review | обидві |
| **Requirements validation** | перевірка, що вимоги справді відповідають потребам замовника | Л7 |
| **Verification** | «Are we building the product **right**?»: чи будуємо продукт правильно (відносно специфікації) | Л8 |
| **Simulation** | імітація роботи системи в різних середовищах, інакше кажучи **тестування програмістом** | Л8 |
| **Verified development** | розробка, яку верифікують на кожному кроці | Л8 |
| **Documentation = inputs for testing** | документація є вхідними даними для тестування (тестувальник перевіряє систему на відповідність документам) | Л8 |

**Запам'ятати:** inspection = процес, review = результат (документ), simulation = тест від програміста.

## 3.2. Validation vs Verification (дуже важливо)

- **Validation** [Л7]: «Чи ми будуємо **той продукт**?» (відповідність реальним потребам замовника).
- **Verification** [Л8]: «Чи ми будуємо продукт **правильно**?» (відповідність специфікації).

Логіка: на етапі специфікації важливо перевірити, що вимоги правильні (validation); на етапі розробки перевірити, що код відповідає цим вимогам (verification).

## 3.3. Flowdown of requirements — V-модель [Л7]

Діаграма у формі літери V.

**Ліва сторона**: вимоги «стікають» вниз, ставши деталізованішими:
Stakeholder → System → Subsystem → Component Requirements.

**Права сторона**: кожному рівню відповідає тест:
Stakeholder Test, System Test, Subsystem Test, Component Test.

**Горизонтальні стрілки** показують, що перевіряється:
- Stakeholder: **validate** the system;
- System: **verify + validate**;
- внизу: **allocate requirements to components** (вимоги розподіляються по компонентах).

Ідея: кожен рівень вимог має власний тест, який перевіряє саме його.

## 4.2. CRC-картка (обидві лекції)

**CRC** = Class – Responsibility – Collaborator.

Картка одного класу (тут **Instructor**):
- **Ліворуч (відповідальності)**: що клас знає й робить: First name, Last name, Address, Unique identifier, Phone number, Add course, Write out master's thesis.
- **Праворуч (співпрацівники)**: з якими класами взаємодіє: Course, Master thesis.

**Чи це класи в коді?** Не зовсім. Це **класи на рівні проєктування**, «кандидати» у класи коду: поняття предметної області, зафіксовані ще до написання коду. У коді частина карток може об'єднатися чи розділитися, а в коді з'являться технічні класи, яких на картці немає. Тож CRC-клас це **кандидат у клас коду**, а не сам клас коду.

У Л7 картка використовується для запису вимог, у Л8 для проєктування модулів.

## 4.3. Формальний метод [Л7]

Математична нотація (схожа на Z). Кожна «схема» описує ситуацію запису людини на курс:

| Схема | Умова | Відповідь |
|-------|-------|-----------|
| **Full1** | кількість записаних `#d = Max` (клас заповнений) | `ClassFull` |
| **AlreadyPresent1** | `p? ∈ d` (людина вже записана) | `AlreadyHere` |
| **Success** | усе добре | `Okay` |

Позначення: `?` = вхід, `!` = вихід, `Ξ` = стан не змінюється.

**Плюс:** абсолютна точність, без двозначності. **Мінус:** важко читати й писати.

## 4.4. Таблиця вимог (Tabular) [Л7]

Стовпці: **RID** (номер вимоги), **опис**, **Priority**, **Risk**, **Workload** (трудомісткість), **ID user story**, яку вимога покриває.

Вимоги ієрархічні:
1. **Нефункціональні технічні** (наприклад, використовувати Java);
2. **Нефункціональні архітектурні** (окремий UI, окрема БД);
3. **Функціональні, пов'язані з даними** (дані викладача, курсу);
4. **Функціональні бізнес-вимоги** (add course, write out master's thesis).

*Функціональні* вимоги описують, **що система робить**. *Нефункціональні* описують, **яка вона** (технології, архітектура, швидкодія).

Таблиця зручна для планування й оцінки (є пріоритет, ризик, трудомісткість) і для відстеження вимог.

## 4.5. User story / Story card [Л7]

Формат: **«Як <роль>, я хочу <дія>, щоб <мета>»**.

Приклад: *Як викладач, я хочу додати курс на семестр, щоб керувати студентами, які хочуть його відвідувати.*

Нижче сценарії:
- **Scen. 1** (викладач): входить, додає курс, бачить заявки студентів, підтверджує їх.
- **Scen. 2** (студент): входить, бачить доступні курси, подає заявки, викладач додає його, якщо є місця.

Історії пишуться простою мовою з погляду користувача.

## 4.6. UML-діаграми: чотири види

| Діаграма | Відповідає на питання | Лекція |
|----------|----------------------|--------|
| **Use case** | **ЩО** користувач може робити із системою | Л7 |
| **Sequence** | **В ЯКОМУ ПОРЯДКУ** взаємодіють об'єкти (час) | обидві |
| **Class** | **З ЧОГО СКЛАДАЄТЬСЯ** система і як частини пов'язані (структура) | Л8 |
| **Deployment** | **ЯКІ ФІЗИЧНІ ФАЙЛИ** і компоненти й як їх розгортати | Л8 |

### Use case [Л7]
Актор **Instructor** поза системою **IS** і три варіанти використання всередині: **add course, log in, assign student**.

### Sequence [обидві]
Об'єкти **Instructor, IS, Course, Database**. Вертикальні лінії це час, стрілки це повідомлення по порядку: sign in → Create (course) → запити до бази (account student, assign student) → відповіді.

### Class diagram [Л8]
Показує **структуру**: які є класи й як вони пов'язані. Приклад: банківські рахунки.
- **Прямокутник** = клас (Bank Account, Savings Account...).
- **Стрілка з порожнім трикутником** = **успадкування** («є різновидом»): Savings Account є різновидом Bank Account.
- **Лінії з числами** = **асоціації** з кратністю: `1` один, `*` багато, `0..1` нуль або один.
- **Курсив** = **абстрактний** клас (лише узагальнює, екземплярів не створюють).
- `{complete, disjoint}` уточнює «розбиття на підкласи» (всі підкласи перелічено / об'єкт належить лише одному). Деталі в дужках напам'ять вчити не обов'язково.

### Deployment diagram [Л8]
Показує, **з яких фізичних файлів складається система** і як вони розгортаються. Приклад: веб-застосунок `book_club_app.war`.
- **Artifact (артефакт)**: фізичний файл чи пакет (`.war`, `web.xml`, `.jar`), можуть лежати у вкладених папках (WEB-INF, lib).
- **Component (компонент)**: логічна частина системи (Shopping Cart, Orders) з інтерфейсами (IShoppingCart, IOrders).
- **Manifestation («manifest»)**: показує, що **артефакт є фізичним втіленням компонента** (наприклад, `shp-cart.jar` це втілення Shopping Cart).

Ідея: component = «що система вміє» (логіка), artifact = «який файл це реалізує» (фізика). Потрібно на етапі інтеграції та випуску.

## 4.7. Вихідний код як документація [Л8]

Тепер, коли код пишеться, **сам код і коментарі в ньому теж є документацією**.

| | Generated (слайд 14) | Handwritten (слайд 15) |
|---|---|---|
| Хто створив | інструмент автоматично | людина |
| Приклад | файл `project1cpp_sc_main.cpp` (C++) з шаблонними коментарями й «callout»-функціями (`UserInitializationCallout` тощо) | код мовою Ada з німецькими коментарями |
| Ознаки | шаблонний вигляд, «хуки» (місця для ручного доповнення користувачем) | докладні коментарі (опис функції, параметрів), змістовні назви змінних |
| Пов'язано з | Code generation, MDA | тезою, що код і коментарі це документація |

# Частина 5. Зміни (Dealing with changes)

Слайд 17 [Л7] і слайд 16 [Л8].

**Спільні три джерела змін:**
1. **Corrections**: виправлення помилок;
2. **Evolution based on self-evaluation**: розвиток на основі самооцінки команди;
3. **Evolution based on acceptance ratio and customer feedbacks**: розвиток на основі рівня прийняття продукту й відгуків замовника.

**[Л8] Додано:**

# Частина 7. Підсумок

## Головна думка

Проєкт проходить від **задуму до працюючої системи**, і менеджер керує цим процесом:

1. **Зрозуміти** проблему й область (аналіз);
2. **Записати** вимоги й оцінити розмір та вартість (специфікація, FPA);
3. **Спроєктувати** систему й розбити на модулі;
4. **Реалізувати** (код, вручну або генерацією) й **зібрати** (інтеграція);
5. **Перевіряти** на кожному кроці (validation → verification, inspection, review, simulation);
6. **Документувати** (CRC, UML, таблиці, user stories, код з коментарями);
7. **Керувати змінами** (корекції, еволюція, версіонування, релізи);
8. **Забезпечувати ресурсами** (люди, ПЗ/обладнання, гроші).

## Шпаргалка для іспиту

**Терміни та різниці**
- **Inspection** = процес, **Review** = результат (документ), **Simulation** = тест від програміста.
- **Validation** (Л7) = «той продукт?», **Verification** (Л8) = «правильно зроблено?».
- **Функціональні** вимоги = що система робить; **нефункціональні** = яка вона.
- **FPA** оцінює розмір системи за функціями й дає вартість та ресурси (UFP/VAF).
- **Module** = мала підсистема, описується (name, responsibility, collaborators).
- **Requirement tracking** = кожен елемент дизайну пов'язаний з вимогою.
- **MDA** = генерація коду з моделей. Код буває **generated** і **handwritten**.
- **Documentation = inputs for testing**.

**Діаграми**
- **Use case**: що можна робити.
- **Sequence**: у якому порядку.
- **Class**: структура й зв'язки.
- **Deployment**: фізичні артефакти й компоненти (artifact, component, manifestation).
- **V-модель**: вимоги спускаються вниз, кожен рівень має свій тест.

**Зміни та ресурси**
- Джерела змін: corrections, самооцінка, acceptance ratio і відгуки; **[Л8]** versioning і release engineering.
- Команда **paid**, замовник **free** (але його час рахується).
- **Soft skills** і **hard skills**.
- Нові ролі в Л8: **Tester**, **Coder**; зникли Indian scout і Puzzle solver.

**Загальне**
- Способи запису вимог: CRC, формальні методи, вільний текст, таблиці, UML, user stories.
- В **agile** документація менш важлива.
