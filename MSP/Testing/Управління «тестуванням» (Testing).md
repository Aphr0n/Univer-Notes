## Чотири рівні тестування
Це **ядро лекції**. Рівні йдуть **від малого до великого**:

> **модуль → взаємодія модулів → система → користувач**

Спочатку дві ключові ідеї, які потрібні для розуміння слайдів.

### Що таке mock і stub (слайди їх не пояснюють, це моє пояснення)
Коли тестуєш одну частину системи, вона зазвичай залежить від інших частин. Щоб не залежати від них, їх **підміняють «заглушками»**:
- **Mock** (мок) = «несправжній» об'єкт, який імітує поведінку іншого модуля (і часто перевіряє, як його викликали).
- **Stub** (стаб) = проста заглушка, що повертає заздалегідь визначені відповіді (наприклад, замість справжнього системного виклику).

*Аналогія:* ви перевіряєте електропроводку, а водопровід ще не готовий. Тому замість справжнього водопроводу ставите тимчасову «іграшкову» заглушку.

На слайдах це допомагає відрізнити рівні: чим вище рівень, тим **менше заглушок і більше справжніх компонентів**.

### Module test (модульне тестування)

- **Separate tests for each subsystem**: для кожної підсистеми (модуля) окремі тести:
  - **name-check**: перевірка за назвою (чи модуль існує й називається як треба);
  - **responsibility-implementation**: чи реалізована його **відповідальність**;
  - **collaborators-interfaces**: чи правильні **інтерфейси** до співпрацівників.
- **More communication/interaction & complex interfaces = mocking other modules, stubbing system calls**: оскільки в модулів багато взаємодій і складні інтерфейси, **інші модулі підміняють моками**, а **системні виклики стабами**.
- **Unit test generation**: **генерація юніт-тестів** (тести можна створювати автоматично).
- **In focus: program units** (на слайді стоїть «I focus», це описка): у фокусі **програмні одиниці** (функції, класи).
- **Writing module test reports**: пишуться звіти про модульне тестування.
- **Checking limits of module functionality and operation**: перевірка **меж** фrнкціональності та роботи модуля.

### Integration test (інтеграційне тестування)

- **No mocks for modules**: модулі **не підміняються** моками; використовуються справжні.
- **System calls might be stubbed**: системні виклики **можуть** бути стабами.
- **Database testing**: тестування бази даних.
- **In focus: the interaction of modules**: у фокусі **взаємодія модулів**.
- **Verification & validation of module/system design**: перевіряється і **верифікація**, і **валідація** дизайну модулів/системи.
- **Writing integration test reports**: звіти про інтеграційне тестування.

### System test (системне тестування)

- **No mocks for modules** і **No stubs for system calls**: **жодних моків і стабів**, усе справжнє.
- **Database testing**: тестування бази даних.
- **Testing interaction with environment**: перевірка **взаємодії із середовищем** (ОС, мережа, обладнання).
- **In focus: the system in its environment**: у фокусі **система в її середовищі**.
- **Validation of system design**: **валідація** дизайну системи.
- **Writing system test reports**: звіти про системне тестування.

### Acceptance test (приймальне тестування)

- **No look inside (black box)**: **«чорна скринька»**: тестувальник не заглядає всередину, лише дивиться на входи й виходи.
- **Real data in the database**: у базі **реальні дані**.
- **Testing user interaction**: перевіряється **взаємодія користувача** із системою.
- **In focus: the user**: у фокусі **користувач**.
- **Validation of system**: **валідація** системи (чи це той продукт, що потрібен).
- **Writing usability reports and change requests**: звіти про **зручність використання** й **запити на зміни** (change requests).

### Порівняльна таблиця чотирьох рівнів

|                               | Module test                              | Integration test         | System test                    | Acceptance test                         |
| ----------------------------- | ---------------------------------------- | ------------------------ | ------------------------------ | --------------------------------------- |
| **У фокусі**                  | програмні одиниці                        | взаємодія модулів        | система в середовищі           | користувач                              |
| **Моки модулів**              | **так**                                  | ні                       | ні                             | ні                                      |
| **Стаби системних викликів**  | **так**                                  | **можуть бути**          | ні                             | ні (не згадано)                         |
| **База даних**                | не згадано                               | тестується               | тестується                     | **реальні дані**                        |
| **Що перевіряють**            | межі функціональності модуля; інтерфейси | взаємодію модулів        | взаємодію із середовищем       | взаємодію користувача                   |
| **Verification / validation** | не вказано                               | **обидва** (V&V дизайну) | **validation** дизайну системи | **validation** системи                  |
| **Підхід**                    | юніт-тести                               | (не вказано)             | (не вказано)                   | **чорна скринька**                      |
| **Що пишуть**                 | module test reports                      | integration test reports | system test reports            | usability reports і **change requests** |

**Закономірність:** що вищий рівень, то **більше справжніх компонентів** (спочатку заглушки скрізь, потім тільки частково, потім ніяких), і то **ближче до користувача**. Також «акцент» зміщується від **verification** (чи правильно зроблено) до **validation** (чи це той продукт).

##  Using requirements in testing (вимоги в тестуванні)
![[Pasted image 20261122012739.png]]

Це **та сама V-модель (Flowdown of requirements)**, що була в лекції 7 (слайд 9), але тепер у контексті тестів.

**Ліва сторона:** вимоги «стікають» вниз: Stakeholder → System → Subsystem → Component Requirements.

**Права сторона:** кожному рівню відповідає тест: Stakeholder Test, System Test, Subsystem Test, Component Test.

**Стрілки:**
- Stakeholder: **validate** the system;
- System: **verify + validate** the system;
- внизу: **allocate requirements to components**.

**Ідея:** вимоги не лише керують розробкою, а й **визначають тести**. Кожен рівень вимог перевіряється відповідним рівнем тестів.

## Test life cycle (життєвий цикл тестування)

![[Pasted image 20261122012807.png]]

Інша версія V-моделі. Це діаграма, що показує, **як кожному етапу розробки відповідає свій рівень тестування**.

**Ліворуч: «Developer's Life Cycle (Verification phase)»**, життєвий цикл **розробника** (фаза верифікації), йде вниз:
- **BRS** (Business requirements specifications): бізнес-вимоги;
- **SRS** (System requirements specifications): системні вимоги;
- **HLD** (High level design): проєкт верхнього рівня;
- **LLD** (Low level design): проєкт нижнього рівня;
- **Coding** → **CODE** (на самому дні «V»).

**Праворуч: «Tester's Life Cycle (Validation phase)»**, життєвий цикл **тестувальника** (фаза валідації), йде вгору:
- **Unit testing**;
- **Component testing**;
- **System integration testing**;
- **System testing**;
- **Acceptance testing**.

**Горизонтальні стрілки** показують відповідність («що перевіряє що»):

| Етап розробки (ліворуч)     | Тест (праворуч)            |
| --------------------------- | -------------------------- |
| Coding                      | Unit testing               |
| LLD (low level design)      | Component testing          |
| HLD (high level design)     | System integration testing |
| SRS (system requirements)   | System testing             |
| BRS (business requirements) | Acceptance testing         |

**Ключова думка:** кожен рівень проєкту має «свій» рівень тестування. Чим вищий рівень вимог, тим ширший тест (бізнес-вимоги перевіряються приймальним тестуванням, а код юніт-тестами).

> Зверніть увагу: діаграма підписує розробника «Verification phase», а тестувальника «Validation phase». Це спрощена схема. На слайдах 5-7 видно, що насправді verification і validation змішані по рівнях (див. таблицю вище). Тож для іспиту краще відтворювати формулювання з конкретних слайдів.

- **Reports using specific templates**: звіти за шаблонами.

## Dealing with changes (робота зі змінами)

- **Retesting and regression testing in case of:** (повторне тестування й регресійне тестування у випадках)
  - **Corrections**: виправлення помилок;
  - **Evolution based on self-evaluation**: розвиток на основі самооцінки;
  - **Evolution based on acceptance ratio and customer feedbacks**: розвиток на основі рівня прийняття й відгуків замовника.
- **Back-to-back testing of components/modules**: «**back-to-back**»-тестування компонентів/модулів. *(Слайд не пояснює; зазвичай це порівняння результатів двох версій або реалізацій на однакових вхідних даних. Уточніть на лекції.)*
- **Versioning & test configurations**: версіонування й **тестові конфігурації** (під кожну версію потрібна своя конфігурація тестів).
- **Release plans imply test strategy**: **плани релізів визначають стратегію тестування**.

Три джерела змін (corrections, самооцінка, відгуки) вже відомі з лекцій 7 і 8. Нове те, що **кожна зміна потребує повторного тестування**.

## The difference: Retest vs Regression test

**Дуже ймовірне екзаменаційне питання.** Це два різних види повторного тестування.

|                            | **Retest (повторне тестування)**                                                           | **Regression test (регресійне тестування)**                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Інша назва                 | **Confirmation testing** (підтверджувальне)                                                | (немає)                                                                                                                                    |
| Що робить                  | запускає **ті тести, що не пройшли минулого разу**, щоб перевірити, чи вдалося виправлення | тестує **раніше протестовану програму після зміни**, щоб переконатися, що **не з'явилися (і не проявилися) дефекти в незмінених частинах** |
| Коли                       | після виправлення помилки                                                                  | коли **змінилося ПЗ або його середовище**                                                                                                  |
| Питання, на яке відповідає | «Чи виправлено ту помилку?»                                                                | «Чи нічого іншого не зламалося через зміну?»                                                                                               |

**Приклад з будинком:**
- *Retest:* текла труба, її полагодили. Перевіряємо ту саму трубу ще раз: тече чи ні?
- *Regression:* поки лагодили трубу, могли зачепити електропроводку чи вентиляцію. Перевіряємо, що вони досі працюють.

**Запам'ятати:** retest = «перевір те, що **зламалося**»; regression = «перевір те, що **працювало**, чи воно не зламалося».

## Підсумок лекції

Тестування це **керований процес перевірки на кількох рівнях**, від найдрібнішого до найширшого:

1. **Module test**: окремі модулі, з моками й стабами;
2. **Integration test**: взаємодія модулів, без моків;
3. **System test**: уся система в середовищі, без моків і стабів;
4. **Acceptance test**: користувач, чорна скринька, реальні дані.

Кожному рівню розробки відповідає свій рівень тестів (**V-модель**). Тести документуються (звіти, test evaluation report), важливі в **agile** (TDD, XP) і потребують повторення після змін (**retest** і **regression test**).

## Шпаргалка для іспиту

**Рівні тестування**
- **Module** = програмні одиниці; **моки модулів + стаби системних викликів**.
- **Integration** = взаємодія модулів; **без моків, стаби можуть бути**; V&V дизайну.
- **System** = система в середовищі; **ні моків, ні стабів**; validation дизайну.
- **Acceptance** = користувач; **black box**; **реальні дані**; validation системи; пишуть usability reports і **change requests**.

**V-модель**
- Coding ↔ Unit testing
- LLD ↔ Component testing
- HLD ↔ System integration testing
- SRS ↔ System testing
- BRS ↔ Acceptance testing

**Якість**
- Module test = якість модуля й коду.
- Integration test = якість інтерфейсів і їх реалізацій.
- System test = пристосування до середовища, конфігурації.
- Acceptance test = якість системи, бізнес-цінність.

**Зміни**
- **Retest (confirmation)** = перевірка виправлення тестів, що **впали**.
- **Regression** = перевірка, що зміна **не зламала незмінені** частини.
- Релізні плани визначають стратегію тестування; тести версіонуються (test configurations).

**Документація та ресурси**
- Тестова документація = «як раніше, але з test» + **test evaluation report**.
- В **agile** тестова документація **важлива** (TDD, XP).
- Ролі: Reporter, Detective, Investigator, Diagnostician, Evaluator, **Tester**, **Coder**.
- SW/HW: Administration, **Test development and run**, Storage.
